# PCIe 6.2 第 3.5 节讲义：Data Link Layer Packets（DLLPs）

> [!abstract] 本讲范围
> 本讲严格围绕 PCI Express Base Specification Revision 6.2 的 **3.5 和 3.5.1**，对应规范页 324-333、截章 PDF 第 16-25 页。
>
> 原文入口：[[01_pcie/attachment/PCIeGen6_chap3.pdf#page=16|PCIeGen6_chap3.pdf，第 16 页]]

## 先回答：Gen6 有了 Flit Mode，还使用 DLLP 吗

**使用。**

Flit Mode 没有废除 DLLP，而是改变了 DLLP 的承载方式和完整性保护方式。

| 问题 | Non-Flit Mode | Flit Mode |
|---|---|---|
| 普通 DLLP 是否仍存在 | 是 | 是 |
| DLLP 怎样传输 | 作为独立的 6-Byte 包传输 | 4-Byte DLLP 内容放入 Flit 的 DLP bytes |
| DLLP 是否有自己的 CRC | 有独立的 16-bit CRC | 没有独立 DLLP CRC，由 Flit 的完整性机制保护 |
| Ack/Nak 是否是 DLLP | 是，使用 Ack/Nak DLLP | 否，使用专用 DLP Symbols |
| 重放单位 | TLP | Flit |
| Flow Control DLLP | InitFC、UpdateFC 等 | 仍使用，还可配合 `Optimized_Update_FC` |
| Link Management DLLP | 对这类编码检查后丢弃 | 用于 L0p Link Management |

所以最准确的说法是：

> **Flit Mode 仍然使用多种 DLLP，但不再使用 Ack DLLP 和 Nak DLLP。**

另外还要区分“设备世代”和“Link 当前运行模式”：

- Gen6-capable 组件与旧组件连接时，为了向后兼容，可以在较低速率和传统模式下工作；
- 64.0 GT/s 链路使用 Flit Mode；
- 因此 PCIe 6.x 规范必须同时定义 Non-Flit Mode 与 Flit Mode 的 DLLP 行为。

## Spec p.324：3.5 从页面底部开始

> 对照页面：[[01_pcie/attachment/PCIeGen6_chap3.pdf#page=16|PDF 第 16 页 / Spec p.324]]

> [!note] 此时先不要研究 Feature 字段
> p.324 只是建立 DLLP 类型清单。具体 `Feature Ack` 和 `Feature Supported` 要到 p.329、图 3-14 才展开。

## Spec p.325：用途列表、通用格式和 Reserved 规则

> 对照页面：[[01_pcie/attachment/PCIeGen6_chap3.pdf#page=17|PDF 第 17 页 / Spec p.325]]

### 原文顺序 1：继续列举 DLLP

p.325 顶部依次列出：

1. `Ack DLLP`
   - 对 TLP Sequence Number 作正向确认；
   - 表示已经成功接收了一批 TLP；
   - 仅用于 Non-Flit Mode。
2. `Nak DLLP`
   - 对 TLP Sequence Number 作负向确认；
   - 用于启动 Data Link Layer Retry；
   - 仅用于 Non-Flit Mode。
3. `InitFC1`、`InitFC2`、`UpdateFC`
   - 用于 Flow Control。
4. Power Management DLLP
   - 用于电源管理。
5. Link Management DLLP
   - 用于 L0p。

读到这里应该立刻做第一次模式分类：

```text
明确标注 NFM only：
    Ack DLLP
    Nak DLLP

没有标注 NFM only：
    InitFC1 / InitFC2 / UpdateFC
    PM DLLP
    其他后续定义的 DLLP
```

这正是“Gen6 Flit Mode 是否还使用 DLLP”的原文证据。

### 原文顺序 2：进入 3.5.1 Rules

接着出现标题：

```text
3.5.1 Data Link Layer Packet Rules
```

后面的内容不再只是介绍，而是形成 DLLP 时必须遵守的格式和处理规则。

### 原文顺序 3：Reserved 字段

规范先规定：

- Transmitter 形成 DLLP 时，Reserved 字段必须全部填 0；
- Receiver 必须忽略 Reserved 字段中的值；
- 编码字段中的 Reserved value 按该字段自己的规则处理。

把发送端和接收端分开记：

```text
发送端合规要求：Reserved = 0
接收端兼容要求：不要解释 Reserved
```

### 原文顺序 4：Non-Flit Mode 通用格式

原文列出三个组成部分：

1. `DLLP Type`；
2. 24-bit `DLLP Type specific information`；
3. 16-bit CRC。

对应图 3-4：

```text
Byte 0      Byte 1      Byte 2      Byte 3      Byte 4-5
+-----------+----------------------------------+----------------+
| DLLP Type | 24-bit Type-specific information| 16-bit CRC     |
+-----------+----------------------------------+----------------+

总计 6 Bytes
```

### 原文顺序 5：Flit Mode 通用格式

Flit Mode 中，原文明确写出 DLLP 在 Flit 的 `DLP bytes` 中传输，并且只由下面两项构成：

1. `DLLP Type`；
2. 24-bit `DLLP Type specific information`。

对应图 3-5：

```text
Byte 0      Byte 1      Byte 2      Byte 3
+-----------+----------------------------------+
| DLLP Type | 24-bit Type-specific information|
+-----------+----------------------------------+

DLLP 内容共 4 Bytes
```

对着两张图时只比较一件事：

```text
图 3-4 比图 3-5 多出的部分 = 16-bit DLLP CRC
```

这说明 Flit Mode 不是没有 DLLP，而是普通 DLLP 不再携带自己的 CRC。

## Spec p.326：Table 3-5 前半

> 对照页面：[[01_pcie/attachment/PCIeGen6_chap3.pdf#page=18|PDF 第 18 页 / Spec p.326]]

这一页几乎全是 `Table 3-5 DLLP Type Encodings`。建议从上向下读，不要先横向背完整张表。

### 原文顺序 1：同一编码在两种模式中可以不同

表的第一行就是最重要的例子：

| Encoding | Non-Flit Mode | Flit Mode |
|---|---|---|
| `0000 0000b` | Ack | NOP2 |

这说明 Type Byte 必须结合当前 Link Mode 解码。

同样：

| Encoding | Non-Flit Mode | Flit Mode |
|---|---|---|
| `0000 0001b` | MRInit，已 Deprecated | Reserved |
| `0001 0000b` | Nak | Reserved |
| `0010 1000b` | Reserved | Link Management |

读这几行的目标不是背数字，而是接受这个事实：

> Non-Flit 和 Flit 使用同一个 8-bit Type 空间，但某些编码会被重新定义。

### 原文顺序 2：两种模式共同使用的固定 Type

接下来可以直接识别：

| Encoding | DLLP |
|---|---|
| `0000 0010b` | Data Link Feature |
| `0010 0000b` | PM_Enter_L1 |
| `0010 0001b` | PM_Enter_L23 |
| `0010 0011b` | PM_Active_State_Request_L1 |
| `0010 0100b` | PM_Request_Ack |
| `0011 0000b` | Vendor-Specific |
| `0011 0001b` | NOP |

### 原文顺序 3：Alternate Protocol 编码

`0000 0011b` 和 `0000 0100b` 是 Alternate Protocol Use 1/2。

规范说明：

- 普通 PCIe 不使用；
- 只有完成 Alternate Protocol 协商后才允许使用；
- 具体语义由 Alternate Protocol 定义，例如 CXL。

### 原文顺序 4：Flow Control 编码开始

表格下半部分开始出现：

- InitFC1-P；
- InitFC1-NP；
- InitFC1-Cpl；
- InitFC2-P；
- InitFC2-NP。

这些编码中有变量位：

```text
bit 3：0 = Shared，1 = Dedicated
bit 2:0：v2 v1 v0，表示 VC 编号
```

因此表里同一个名称会出现两行编码，不是重复，而是分别覆盖 Shared 和 Dedicated。

p.326 到页尾只列到 InitFC2-NP，剩余内容在 p.327。

## Spec p.327：Table 3-5 结束，随后开始逐类型规则

> 对照页面：[[01_pcie/attachment/PCIeGen6_chap3.pdf#page=19|PDF 第 19 页 / Spec p.327]]

### 原文顺序 1：完成 Table 3-5

本页先补完：

- InitFC2-Cpl；
- Deprecated MRInitFC2；
- UpdateFC-P；
- UpdateFC-NP；
- UpdateFC-Cpl；
- Deprecated MRUpdateFC；
- 其他所有编码为 Reserved。

把 Flow Control Type 的高位模式放在一起看：

| Type 高位                  | 含义                      |
| ------------------------ | ----------------------- |
| `0100` / `0101` / `0110` | InitFC1 的 P / NP / Cpl  |
| `1100` / `1101` / `1110` | InitFC2 的 P / NP / Cpl  |
| `1000` / `1001` / `1010` | UpdateFC 的 P / NP / Cpl |

### 原文顺序 2：Table 3-5 的三条注释

表格结束后有三条 Note：

1. `MRInit` 属于已 Deprecated 的 MR-IOV；
2. 其他 MR-IOV 编码只有在 MRInit 成功后才使用；
3. Receiver 不支持的 DLLP Type 被静默忽略。

第三条是当前最有用的：

```text
CRC/Flit 完整性正确，但 Type 不支持
                  |
                  v
             静默丢弃
```

“不支持”本身不构成 Link 错误。

### 原文顺序 3：提醒图 3-6 至图 3-15 省略 CRC

规范紧接着提醒：

- 后续图 3-6 至图 3-15 不画 16-bit CRC；
- 在 Non-Flit Mode 中，CRC 仍然存在；
- 应按图 3-4 把 CRC 接在 4-Byte DLLP 内容之后。

这句话是对照 Spec 时非常容易漏掉的总规则。

### 原文顺序 4：Ack/Nak DLLP 规则

按原文顺序有三点：

1. `AckNak_Seq_Num` 指明哪些 TLP 受到影响；
2. 发送和接收的详细规则在 3.6；
3. Ack/Nak DLLP 不用于 Flit Mode，Ack 编码在 Flit Mode 被 NOP2 复用。

所以本节只定义格式和用途，真正的 Ack/Nak 状态推进、Retry Buffer 清除和 Replay 要到 3.6。

### 原文顺序 5：InitFC1/InitFC2/UpdateFC 规则开始

随后开始解释字段：

- `HdrFC`：对应 P、NP 或 Cpl 的 Header Credit；
- `DataFC`：对应 P、NP 或 Cpl 的 Data Payload Credit；
- 支持 Scaled Flow Control 时，`HdrScale` 和 `DataScale` 给出缩放；
- 不支持时，Scale 字段为 Reserved。

这一组规则在 p.328 继续。

## Spec p.328：Flow Control 规则结束，随后是 PM/Vendor/NOP

> 对照页面：[[01_pcie/attachment/PCIeGen6_chap3.pdf#page=20|PDF 第 20 页 / Spec p.328]]

### 原文顺序 1：Scaled Flow Control 的发送条件

页面开头继续上一页的 FC DLLP：

1. Scaled Flow Control 激活时，InitFC1、InitFC2、UpdateFC 中的 Scale 必须为 `01b`、`10b` 或 `11b`；
2. UpdateFC 想发送非零 Scale，需要同时满足：
   - Transmitter 支持 Scaled Flow Control；
   - 当前 Link 已激活 Scaled Flow Control；
   - 这个 VC 的初始化 DLLP 中，已经从对端收到相应的非零 Scale。

第二条的核心是：

> 运行期 UpdateFC 不能单方面突然改变双方对 Credit 缩放的理解。

### 原文顺序 2：Optimized_Update_FC

接下来转入 Flit Mode：

- Flit Mode 除 UpdateFC DLLP 外，还支持 `Optimized_Update_FC`；
- Optimized 形式没有 HdrScale/DataScale；
- 因此必须沿用初始化时建立的 Scale；
- 为了调试和分析工具可观察性，仍要周期性发送普通 UpdateFC DLLP；
- 原文在这里给出 `10 μs` 相关要求；
- 有 Credit 需要释放时，强烈建议在有有限、非零 Credit 的 VC 之间轮转发送 Optimized Update。

此处应得到结论：

```text
Optimized_Update_FC = 快速常用路径
UpdateFC DLLP       = 仍保留的完整/可观察路径
```

### 原文顺序 3：FC DLLP 何时产生、交给谁

规范随后说明：

- 初始化 VC 时，由 Data Link Layer 触发 InitFC/UpdateFC 相关发送；
- 初始化完成后，按 2.6 的规则由 Transaction Layer 的 Flow Control 状态推动更新；
- 接收端先做完整性检查；
- 正确时把 DLLP 内容交给 Transaction Layer；
- 检查失败则丢弃；
- InitFC1/InitFC2 只用于 VC 初始化。

### 原文顺序 4：Table 3-6

Table 3-6 给出：

| Scale | 是否支持缩放 | Factor | 直觉 |
|---|---|---:|---|
| `00b` | 否 | 1 | 未启用 scaled FC |
| `01b` | 是 | 1 | 支持，但不放大 |
| `10b` | 是 | 4 | Credit 以 4 为粒度 |
| `11b` | 是 | 16 | Credit 以 16 为粒度 |

表里的 `HdrFC[9:2]`、`HdrFC[11:4]` 等写法表示发送时省略必为 0 的低位，接收端再根据 Scale 恢复完整 Credit 值。

### 原文顺序 5：PM DLLP

紧接着是 Power Management：

- 由组件的 Power Management logic 触发发送；
- 接收端完成完整性检查后，交给 Power Management logic。

### 原文顺序 6：Vendor-Specific DLLP

原文使用“recommended”而不是绝对禁止：

- 未通过实现特定机制启用时，建议 Receiver 静默忽略；
- 未启用时，建议 Transmitter 不发送。

### 原文顺序 7：NOP/NOP2

本页最后规定：

- Receiver 完成数据完整性检查后，不执行动作并丢弃 NOP/NOP2；
- 除非其他规则另有规定。

具体格式在下一页的图 3-7、3-8。

## Spec p.329：Feature/Link Management 规则和图 3-6 至图 3-8

> 对照页面：[[01_pcie/attachment/PCIeGen6_chap3.pdf#page=21|PDF 第 21 页 / Spec p.329]]

### 原文顺序 1：Data Link Feature DLLP

两条字段规则：

1. `Feature Ack = 1b`
   - 表示发送此 DLLP 的 Port 已经收到对端的 Data Link Feature DLLP。
2. `Feature Supported`
   - 表示发送 Port 支持的数据链路 Feature 或属性；
   - 各 bit 的意义由 Table 3-1 定义。

注意 `Feature Ack` 不是“所有 Feature 都协商成功”，它首先表示“我已经收到你的 Feature DLLP”。

### 原文顺序 2：Link Management DLLP

规范只在这里强调一条模式规则：

- Non-Flit Mode Receiver 收到 Link Management 编码后，完成完整性检查，再不采取动作并丢弃。

因为这个 DLLP 的实际用途属于 Flit Mode L0p。

### 原文顺序 3：Figure 3-6 Ack/Nak

图中需要识别：

- Ack Type：`0000 0000b`；
- Nak Type：`0001 0000b`；
- `AckNak_Seq_Num`；
- 其余 Reserved 位。

图标题明确写着 `Non-Flit Mode`。不要把它套到 Flit Mode。

### 原文顺序 4：Figure 3-7 NOP

图中：

- Type 为 `0011 0001b`；
- 后面的 Type-specific information 可以是 arbitrary value；
- 接收端检查后丢弃。

### 原文顺序 5：Figure 3-8 NOP2

图标题明确写 `Flit Mode`：

- Type 为 `0000 0000b`；
- 后续 24 bits 必须为 0。

把图 3-6 和图 3-8 并排看，就能看到 `0000 0000b` 在两种模式中的复用。

## Spec p.330：Figure 3-9 与 Figure 3-10

> 对照页面：[[01_pcie/attachment/PCIeGen6_chap3.pdf#page=22|PDF 第 22 页 / Spec p.330]]

这一页没有新段落，主要任务是读懂 InitFC1 和 InitFC2 的字段图。

### Figure 3-9：InitFC1

按从左到右读：

1. Byte 0：
   - Type 高位区分 P、NP、Cpl；
   - bit 3 区分 Shared/Dedicated；
   - bit 2:0 是 VC。
2. Byte 1：
   - `HdrFC`。
3. Byte 2：
   - 包含 `HdrScale`、`DataScale` 和 DataFC 的高位部分。
4. Byte 3：
   - DataFC 的其余部分。

字段组合表达：

> “某个 VC、某种 P/NP/Cpl 类型的 Header/Data 接收资源，在 FC_INIT1 中怎样通告。”

### Figure 3-10：InitFC2

字段排布与 InitFC1 基本相同，主要区别是 DLLP Type 高位编码变成 InitFC2。

因此不要重新学一遍所有字段，只需确认：

```text
InitFC1：第一阶段初始化通告
InitFC2：第二阶段确认/推进
```

### 图中的 Flit Mode 零值注释

图 3-9、3-10 还在 HdrScale/DataScale 附近标出 Flit Mode 的特殊零值语义：

- Infinite Credits；
- Zero Credits；
- Merged Shared Credits。

所以看到 `HdrFC = 00h` 或 `DataFC = 000h` 时，必须结合 Scale/模式解释，不能直接翻译为“Credit 为 0”。

## Spec p.331：UpdateFC、PM、Vendor-Specific 三张图

> 对照页面：[[01_pcie/attachment/PCIeGen6_chap3.pdf#page=23|PDF 第 23 页 / Spec p.331]]

### 原文顺序 1：Figure 3-11 UpdateFC

字段排布继续复用 InitFC 的结构：

- Byte 0：UpdateFC-P/NP/Cpl、Shared/Dedicated、VC；
- HdrFC/HdrScale；
- DataFC/DataScale。

与 InitFC 图的主要差异不是 Credit 字段本身，而是用途：

```text
InitFC1/2：建立初始 Flow Control 状态
UpdateFC ：运行过程中归还/更新 Credit
```

### 原文顺序 2：Figure 3-12 Power Management

图中 Byte 0 选择：

- PM_Enter_L1；
- PM_Enter_L23；
- PM_Active_State_Request_L1；
- PM_Request_Ack。

# 第二部分：按主题理解与复习

> [!note] 这一部分的定位
> 上面的“第一部分”用于陪你逐页读 Spec；下面保留原讲义的主题化整理，用于读完原文后建立整体模型和复习。

# 0. 先建立正确的分层关系

## 0.1 TLP 是业务，DLLP 是当前 Link 的控制

### TLP：Transaction Layer Packet

TLP 承载实际事务，例如：

- Memory Read；
- Memory Write；
- Configuration Read/Write；
- Completion；
- Message。

TLP 可能经过 Switch，跨越多条 Link。

### DLLP：Data Link Layer Packet

DLLP 是两个直接相连 Port 的数据链路层之间交换的控制消息，例如：

- 对 TLP 的确认和否认；
- Flow Control 初始化和 Credit 更新；
- 电源管理；
- 数据链路特性交换；
- L0p Link Management。

DLLP 只对当前一条 Link 有效，不会经过 Switch 路由。

```text
Root Port ---- Link 1 ---- Switch ---- Link 2 ---- Endpoint

TLP：
Root Port ================================> Endpoint
                     Switch 路由

DLLP：
Root Port <----------> Switch Port
                       Switch Port <----------> Endpoint
        Link 1 独立                   Link 2 独立
```

## 0.2 DLLP、DLP 与 DLP Symbol 不是同一概念

| 名称 | 是什么 |
|---|---|
| DLLP | 一条具有明确语义的数据链路层协议消息 |
| DLP bytes | Flit 中固定的数据链路控制区域 |
| DLLP Payload | DLP 区域中可承载的 4-Byte 普通 DLLP 内容 |
| DLP Symbol | Flit Mode DLP 中的专用控制编码，例如 Ack/Nak |

关系可以画成：

```text
Flit 的 DLP 信息
│
├── 普通 DLLP
│   ├── InitFC1 / InitFC2
│   ├── UpdateFC
│   ├── Data Link Feature
│   ├── Power Management
│   └── Link Management
│
├── Optimized_Update_FC
├── Flit_Marker
└── 专用 Ack/Nak DLP Symbols
```

> [!important] 一句话区分
> DLLP 说明“要告诉对端什么”；DLP 说明“Flit 把数据链路控制信息放在哪里”。

# 1. 规范 p.324-325：DLLP 种类与通用格式

> 原文页面：
> [[01_pcie/attachment/PCIeGen6_chap3.pdf#page=16|PDF 第 16 页 / Spec p.324]]；
> [[01_pcie/attachment/PCIeGen6_chap3.pdf#page=17|PDF 第 17 页 / Spec p.325]]

## 1.1 第 3.5 节列出的 DLLP 家族

| DLLP 家族              | 主要作用                               | 模式说明                |
| -------------------- | ---------------------------------- | ------------------- |
| Data Link Feature    | 协商支持的数据链路特性                        | Flit/Non-Flit 都可能使用 |
| Ack                  | 确认一批 TLP 已正确接收                     | 仅 Non-Flit Mode     |
| Nak                  | 请求 Data Link Layer Retry           | 仅 Non-Flit Mode     |
| InitFC1 / InitFC2    | 初始化 Virtual Channel 的 Flow Control | 两种模式都使用             |
| UpdateFC             | 更新接收端可用 Credit                     | 两种模式都使用             |
| PM DLLP              | Link 电源管理                          | 两种模式都使用             |
| Link Management DLLP | L0p Link 管理                        | Flit Mode 使用        |
| Vendor-Specific      | 厂商自定义                              | 需要实现相关使能机制          |
| NOP / NOP2           | 不执行普通动作的占位/特殊控制                    | NOP2 为 Flit Mode 定义 |

这张表直接回答了“Gen6 是否还用 DLLP”：不仅用，而且 Flow Control、Power Management、Feature Exchange 和 L0p 都依赖相应的数据链路控制信息。

## 1.2 Reserved 字段的规则

形成 DLLP 时：

- 所有标为 Reserved 的字段必须填 0；
- Receiver 必须忽略 Reserved 字段中的值；
- 如果是某个编码字段里的 Reserved value，则按该字段自己的规则处理。

发送端和接收端的规则并不矛盾：

```text
发送端：必须规范地产生 0
接收端：不能因为未来版本使用这些位而错误解释当前包
```

> [!warning] “接收端忽略”不等于“发送端可以随便填”
> Reserved 位填 0 是发送端的合规要求；接收端忽略是为了版本演进与鲁棒性。

## 1.3 Non-Flit Mode DLLP：6 Bytes

通用格式为：

```text
Byte 0       Byte 1       Byte 2       Byte 3       Byte 4       Byte 5
+------------+--------------------------------------+-------------------------+
| DLLP Type  | 24-bit DLLP Type specific info      | 16-bit DLLP CRC         |
+------------+--------------------------------------+-------------------------+
     1B                       3B                              2B
```

总长度：

```text
1 Byte Type + 3 Bytes Type-specific information + 2 Bytes CRC
= 6 Bytes
```

这里的 CRC 是这个 DLLP 自己的链路级完整性保护。

## 1.4 Flit Mode 中的 DLLP：4 Bytes

Flit Mode 的普通 DLLP 内容为：

```text
Byte 0       Byte 1       Byte 2       Byte 3
+------------+--------------------------------------+
| DLLP Type  | 24-bit DLLP Type specific info      |
+------------+--------------------------------------+
     1B                       3B
```

它被放入 Flit 的 DLP bytes 中。

没有附加独立的 16-bit DLLP CRC，因为 DLP 与 TLP Bytes 一起受到整个 Flit 的 CRC/FEC 保护。接收端先判断 Flit 是否有效，再处理其中的 DLLP。

```text
Non-Flit：
[ 4B DLLP 内容 ][ 2B DLLP CRC ]

Flit：
[ 一个 Flit：TLP Bytes | DLP（包含 4B DLLP）| Flit CRC | FEC ]
```

# 2. 规范 p.326-327：怎样读 DLLP Type 编码

> 原文页面：
> [[01_pcie/attachment/PCIeGen6_chap3.pdf#page=18|PDF 第 18 页 / Spec p.326]]；
> [[01_pcie/attachment/PCIeGen6_chap3.pdf#page=19|PDF 第 19 页 / Spec p.327]]

## 2.1 Type Byte 是 DLLP 的“消息名称”

DLLP 的第一个 Byte 告诉接收端：

- 这是不是 Flow Control 信息；
- 是 Ack、PM，还是 Feature Exchange；
- 如果是 Flow Control，它属于哪类 Credit；
- 它属于哪个 VC；
- 使用 Shared 还是 Dedicated Flow Control。

不需要一开始背下 Table 3-5 的所有二进制值。先按功能分组。

## 2.2 常用固定编码

| Type Byte | Non-Flit Mode              | Flit Mode              |
| --------: | -------------------------- | ---------------------- |
|     `00h` | Ack DLLP                   | NOP2 DLLP              |
|     `02h` | Data Link Feature DLLP     | Data Link Feature DLLP |
|     `10h` | Nak DLLP                   | Reserved               |
|     `20h` | PM_Enter_L1                | PM_Enter_L1            |
|     `21h` | PM_Enter_L23               | PM_Enter_L23           |
|     `23h` | PM_Active_State_Request_L1 | 同左                     |
|     `24h` | PM_Request_Ack             | 同左                     |
|     `28h` | Reserved                   | Link Management        |
|     `30h` | Vendor-Specific            | Vendor-Specific        |
|     `31h` | NOP                        | NOP                    |

> [!important] 同一个编码可以随模式改变含义
> `00h` 在 Non-Flit Mode 是 Ack，在 Flit Mode 是 NOP2。因为 Link 两端已经知道当前运行模式，所以不会产生解析歧义。

Ack/Nak 的模式差异尤其重要：

- `Ack DLLP`、`Nak DLLP` 仅用于 Non-Flit Mode；
- Flit Mode 中 `10h` 不再表示 Nak，而是 Reserved；
- Flit Mode 的 Ack/Nak 由 DLP 的专用 Replay Command/DLP Symbol 编码承担；
- 因此不能在 Flit Mode 中寻找一个传统的 Ack DLLP。

## 2.3 Flow Control DLLP 的编码是“类型 + 属性”

Flow Control DLLP 的 Type Byte 不是单纯固定常数，而是把多个信息压入同一 Byte：

```text
bit 7:4：DLLP 家族和 Credit 类别
bit 3  ：Shared / Dedicated Flow Control
bit 2:0：VC[2:0]
```

主要家族：

| 高位模式        | DLLP         |
| ----------- | ------------ |
| `0100 xxxx` | InitFC1-P    |
| `0101 xxxx` | InitFC1-NP   |
| `0110 xxxx` | InitFC1-Cpl  |
| `1100 xxxx` | InitFC2-P    |
| `1101 xxxx` | InitFC2-NP   |
| `1110 xxxx` | InitFC2-Cpl  |
| `1000 xxxx` | UpdateFC-P   |
| `1001 xxxx` | UpdateFC-NP  |
| `1010 xxxx` | UpdateFC-Cpl |

其中：

- `P`：Posted，请求不需要 Completion，例如常见 Memory Write；
- `NP`：Non-Posted，请求需要 Completion，例如 Memory Read；
- `Cpl`：Completion，对 NP 请求的响应；
- bit 3 为 0：Shared Flow Control；
- bit 3 为 1：Dedicated Flow Control；
- bit 2:0：Virtual Channel 编号。

因此接收端只看 Byte 0，就能知道：

```text
这是 Init 还是 Update
    +
是 P / NP / Cpl 哪一类 Credit
    +
属于哪个 VC
    +
是 Shared 还是 Dedicated
```

## 2.4 Deprecated、Alternate Protocol 与 Unsupported

Table 3-5 还包含三类不应混入主线记忆的编码：

### Deprecated MR-IOV

一些编码曾用于 MR-IOV，现已 Deprecated。在 Flit Mode 中对应位置通常为 Reserved。

### Alternate Protocol Use 1/2

`03h`、`04h` 不由 PCIe 普通协议使用。只有完成 Alternate Protocol 协商以后，才允许按对应协议解释，例如 CXL。

### Unsupported DLLP Type

Receiver 不支持的 DLLP Type 应静默忽略。

静默忽略的含义是：

- 不把它当成当前支持的控制命令执行；
- 不因为“不认识”就破坏 Link；
- 允许新版本/可选特性与旧接收端共存。

# 3. 规范 p.327-330：各 DLLP 家族的规则

> 原文页面：
> [[01_pcie/attachment/PCIeGen6_chap3.pdf#page=19|PDF 第 19 页 / Spec p.327]]；
> [[01_pcie/attachment/PCIeGen6_chap3.pdf#page=20|PDF 第 20 页 / Spec p.328]]；
> [[01_pcie/attachment/PCIeGen6_chap3.pdf#page=21|PDF 第 21 页 / Spec p.329]]；
> [[01_pcie/attachment/PCIeGen6_chap3.pdf#page=22|PDF 第 22 页 / Spec p.330]]

## 3.1 Ack 与 Nak：只属于 Non-Flit Mode

Ack/Nak DLLP 中的 `AckNak_Seq_Num` 指明哪些 TLP 受到影响。

### Ack

Ack 表示：

> 截至某个 TLP Sequence Number 的一批 TLP 已被正确接收。

发送端据此清除 Retry Buffer 中已经确认的 TLP。

### Nak

Nak 表示：

> 接收端发现错误或序号问题，请发送端启动 Data Link Layer Retry。

### 为什么 Flit Mode 不再用它们

Non-Flit Mode 的 Sequence Number 和 Retry 以 TLP 为中心，所以需要 Ack/Nak DLLP 携带 TLP 序号。

Flit Mode 的 Sequence Number 和 Replay 以 Flit 为中心，Ack/Nak 已进入 DLP 的专用 Replay Command/Symbol 字段。继续使用 TLP-level Ack/Nak DLLP 会重复甚至冲突。

```text
Non-Flit：
TLP Seq -> Ack/Nak DLLP -> TLP Replay

Flit：
Flit Seq -> DLP Ack/Nak Symbol -> Flit Replay
```

## 3.2 InitFC1、InitFC2 与 UpdateFC

这三类 DLLP 都携带 Flow Control Credit。

| 字段 | 含义 |
|---|---|
| HdrFC | 某类 TLP Header 的 Credit 值 |
| DataFC | 某类 TLP Data Payload 的 Credit 值 |
| HdrScale | Header Credit 的缩放因子 |
| DataScale | Data Credit 的缩放因子 |
| VC[2:0] | Credit 属于哪个 Virtual Channel |
| P / NP / Cpl | Credit 属于 Posted、Non-Posted 或 Completion |

### InitFC1 / InitFC2

只用于 VC 的 Flow Control 初始化：

```text
FC_INIT1：初次交换接收能力
     |
     v
FC_INIT2：确认双方已经获得初始化信息
     |
     v
VC 可以进入正常 Flow Control 工作
```

### UpdateFC

初始化完成后，用于告诉发送端：

> 接收端释放了新的缓冲区资源，你现在又可以发送更多相应类型的 TLP。

## 3.3 Scaled Flow Control

高速 Link 的往返时延内可能存在很多在途数据，传统 Credit 字段表示范围可能不足，因此使用缩放因子扩大范围。

| HdrScale/DataScale | 是否支持缩放 | Scaling Factor |
| ------------------ | ------ | -------------: |
| `00b`              | 否      |              1 |
| `01b`              | 是      |              1 |
| `10b`              | 是      |              4 |
| `11b`              | 是      |             16 |

直觉上：

```text
字段里传 20，Scale = 1   -> 表示 20 个单位
字段里传 20，Scale = 4   -> 表示 80 个单位
字段里传 20，Scale = 16  -> 表示 320 个单位
```

实际编码通过省略必为 0 的低位并在接收端恢复来扩大可表示范围。

规范要求：

- 激活 Scaled Flow Control 后，InitFC1、InitFC2 和 UpdateFC 中的 Scale 字段使用 `01b`、`10b` 或 `11b`；
- UpdateFC 只有在双方通过初始化建立了相应缩放条件后，才允许发送非零 Scale；
- 不支持 Scaled Flow Control 时，相应 Scale 字段是 Reserved。

## 3.4 Flit Mode 中为什么还有 UpdateFC DLLP

Flit Mode 除了普通 UpdateFC DLLP，还支持 `Optimized_Update_FC`。

但是：

> `Optimized_Update_FC` 是补充，不是把 UpdateFC DLLP 完全删除。

原因包括：

- Optimized 形式没有 HdrScale/DataScale 字段；
- Receiver 必须使用初始化阶段已建立的 Scale 来解释它；
- 普通 UpdateFC DLLP仍用于携带完整的缩放 Credit 信息；
- 规范保留周期性的普通 UpdateFC DLLP，便于调试工具和逻辑分析仪观察。

阅读原文中的 `10 μs` 要求时，可以先理解成：

> 即使实现使用 Optimized_Update_FC 加速常见 Credit 返回，也必须周期性发送可观察的普通 UpdateFC DLLP，并按 VC 提供相应的 scaled credit 信息。

## 3.5 Flow Control DLLP 的接收路径

```text
收到 InitFC / UpdateFC
          |
          v
Data Link Layer 检查完整性
          |
          +-- 失败：丢弃
          |
          +-- 正确：把 Credit 信息交给 Transaction Layer
```

完整性检查的位置与模式有关：

- Non-Flit Mode：检查 DLLP 自己的 16-bit CRC；
- Flit Mode：先在 Flit level 判断完整性，不再对 4-Byte DLLP 单独做 CRC 检查。

# 4. 规范 p.328-332：其他 DLLP

> 原文页面：
> [[01_pcie/attachment/PCIeGen6_chap3.pdf#page=20|PDF 第 20 页 / Spec p.328]]；
> [[01_pcie/attachment/PCIeGen6_chap3.pdf#page=21|PDF 第 21 页 / Spec p.329]]；
> [[01_pcie/attachment/PCIeGen6_chap3.pdf#page=23|PDF 第 23 页 / Spec p.331]]；
> [[01_pcie/attachment/PCIeGen6_chap3.pdf#page=24|PDF 第 24 页 / Spec p.332]]

## 4.1 Power Management DLLP

常见 Type：

| Type | 含义 |
|---:|---|
| `20h` | PM_Enter_L1 |
| `21h` | PM_Enter_L23 |
| `23h` | PM_Active_State_Request_L1 |
| `24h` | PM_Request_Ack |

这些 DLLP 的发送由组件的 Power Management logic 触发。

接收端：

1. 先由数据链路层确认其完整性；
2. 再把消息交给组件的电源管理逻辑。

数据链路层负责可靠承载，电源管理逻辑负责解释“进入哪个低功耗状态”。

## 4.2 Vendor-Specific DLLP

Type 为 `30h`，后面的 24 bits 由厂商定义。

规范建议：

- 除非实现特定机制已启用，否则 Receiver 静默忽略；
- 除非实现特定机制已启用，否则 Transmitter 不应发送。

这防止不同厂商把相同 24-bit 空间解释为不同命令。

## 4.3 NOP 与 NOP2

### NOP DLLP

- Type 为 `31h`；
- 24-bit Type-specific information 可以是任意值；
- Receiver 完成完整性检查后，不执行普通动作并丢弃。

### NOP2 DLLP

- Flit Mode 使用；
- Type 编码为 `00h`，即复用 Non-Flit Ack 的编码；
- 其余 24 bits 必须为 0。

```text
Non-Flit 00h -> Ack
Flit     00h -> NOP2
```

NOP/NOP2 的重点不是承载业务，而是提供合法的空操作或满足某些协议/实现需要。

## 4.4 Data Link Feature DLLP

Type 为 `02h`，24-bit 信息区域包含：

- `Feature Ack`；
- `Feature Supported`。

`Feature Ack = 1b` 表示：

> 本 Port 已经收到对端的 Data Link Feature DLLP。

`Feature Supported` 表示本 Port 支持的数据链路 Feature 或相关属性。

这就是 DLCMSM 的 `DL_Feature` 状态实际交换的消息。

```text
Port A                                Port B

Feature Supported(A)  -------------->
                          <------------  Feature Supported(B)

Feature Ack = 1         -------------->
                          <------------  Feature Ack = 1
```

## 4.5 Link Management DLLP

Type 为 `28h`，用于 Flit Mode 下的 L0p Link Management。

它的 Type-specific information 包含：

- Link Management Type；
- L0p Priority；
- L0p Command；
- Response Payload；
- Link Width。

在 Non-Flit Mode 中，这个编码是 Reserved。Receiver 检查完整性后必须不采取动作并丢弃。

这再次说明：

> 不是所有 DLLP 都同时适用于两种模式。

```text
如果当前为 Non-Flit Mode：
图 3-6 至 3-15 中的 4 Bytes + Figure 3-4 的 2-Byte CRC

如果当前为 Flit Mode：
图中的 4 Bytes 放入 Flit DLP，不追加 DLLP CRC
```

> [!warning] 图中没画 CRC，不等于 Non-Flit DLLP 没有 CRC
> 规范在 p.327 明确说明，图 3-6 至 3-15 省略了 CRC；Non-Flit Mode 必须按图 3-4 加上。

## 5.2 Flow Control 图的阅读顺序

以 InitFC/UpdateFC 为例：

```text
+--------------------+----------------+----------------+
| Type/VC/Shared位   | HdrFC + Scale  | DataFC + Scale |
+--------------------+----------------+----------------+
```

建议按以下顺序读：

1. 是 InitFC1、InitFC2 还是 UpdateFC？
2. 是 P、NP 还是 Cpl？
3. VC 是多少？
4. Shared 还是 Dedicated？
5. HdrFC 值是多少，HdrScale 是多少？
6. DataFC 值是多少，DataScale 是多少？

不要一上来逐 bit 背图，否则很容易忘记这些字段共同表达的是：

> “某个 VC、某个事务类别的接收缓冲区，现在有多少 Header/Data Credit。”

## 5.3 Flit Mode 中零 Credit 编码有额外语义

图 3-9 和图 3-10 对 Flit Mode 的零值给出特殊解释，例如：

- 表示 Infinite Credits；
- 表示 Zero Credits；
- 表示 Merged Shared Credits。

这些含义需要与 Scale 字段和 Shared/Dedicated 状态一起解释，不能只看到 `HdrFC = 0` 或 `DataFC = 0` 就武断地说“没有 Credit”。

# 6. 规范 p.332-333：Non-Flit DLLP 的 16-bit CRC

> 原文页面：
> [[01_pcie/attachment/PCIeGen6_chap3.pdf#page=24|PDF 第 24 页 / Spec p.332]]；
> [[01_pcie/attachment/PCIeGen6_chap3.pdf#page=25|PDF 第 25 页 / Spec p.333]]

## 6.1 适用范围

这部分只适用于 Non-Flit Mode。

```text
Non-Flit DLLP：有独立 16-bit CRC
Flit Mode DLLP：无独立 DLLP CRC，完整性在 Flit level 处理
```

## 6.2 计算参数

规范规定：

- CRC polynomial coefficient：`100Bh`；
- 初始值/seed：`FFFFh`；
- 从 Byte 0 的 bit 0 开始；
- 每个 Byte 按 bit 0 到 bit 7 的方向处理；
- DLLP 的所有位都参加计算，包括 Reserved 位；
- 计算结果取反后放入 16-bit CRC 字段。

可以按流程记：

```text
CRC register = FFFFh
       |
       v
从 DLLP Byte 0 bit 0 开始
逐 Byte、每 Byte 从 bit 0 处理到 bit 7
       |
       v
使用 100Bh 对应的 CRC 运算
       |
       v
结果取反
       |
       v
按 Table 3-7 的 bit mapping 放入 CRC 字段
```

## 6.3 为什么 Reserved 位也必须参加 CRC

CRC 保护的是实际传输的全部 DLLP 内容，而不是只保护接收端当前理解的字段。

如果 Reserved 位不参加：

- 传输中 Reserved 位发生翻转可能无法被 CRC 检出；
- 未来版本赋予这些位新含义时，保护范围会不一致。

所以必须：

```text
发送端把 Reserved 填 0
            +
CRC 仍覆盖这些 0
```

## 6.4 Table 3-7 的 bit mapping

映射可概括为每个 8-bit 组内部反序：

```text
CRC result bit 0  -> CRC field bit 7
CRC result bit 1  -> CRC field bit 6
...
CRC result bit 7  -> CRC field bit 0

CRC result bit 8  -> CRC field bit 15
CRC result bit 9  -> CRC field bit 14
...
CRC result bit 15 -> CRC field bit 8
```

实现或对照波形时，不能直接把软件计算出的 16-bit 数值按人类常见的高位到低位顺序抄入链路字段，必须遵守规范的 bit mapping。

# 7. 两种模式下发送一个 UpdateFC 的完整过程

## 7.1 Non-Flit Mode

```text
接收端释放了一批缓冲区
        |
        v
生成 UpdateFC：
Type + VC + P/NP/Cpl + HdrFC/DataFC + Scale
        |
        v
形成 4-Byte DLLP 内容
        |
        v
计算并追加 16-bit DLLP CRC
        |
        v
作为独立 6-Byte DLLP 发送
        |
        v
对端检查 DLLP CRC
        |
        +-- 错误：丢弃
        |
        +-- 正确：把 Credit 信息交给 Transaction Layer
```

## 7.2 Flit Mode

```text
接收端释放了一批缓冲区
        |
        v
生成普通 UpdateFC DLLP
或选择 Optimized_Update_FC
        |
        v
把控制信息放入当前 Flit 的 DLP bytes
        |
        v
和 TLP Bytes 一起接受 Flit CRC/FEC 保护
        |
        v
发送整个 Flit
        |
        v
对端先验证/纠正 Flit
        |
        +-- Flit invalid：按 Flit Replay 规则处理
        |
        +-- Flit valid：解释其中的 UpdateFC
```

两种模式的业务目的相同：

> 告诉对端“我又释放了一些接收资源”。

改变的是承载、校验和错误恢复单位。

# 8. 哪些 DLLP 在 Flit Mode 中还存在

## 8.1 继续使用的

- Data Link Feature DLLP；
- InitFC1；
- InitFC2；
- UpdateFC；
- PM DLLP；
- Vendor-Specific DLLP；
- NOP/NOP2；
- Link Management DLLP。

## 8.2 不再作为 DLLP 使用的

- Ack DLLP；
- Nak DLLP。

Flit Mode 使用专用 DLP Ack/Nak 编码，并以 Flit 为确认和重放单位。

## 8.3 新增或强化的 Flit Mode 控制形式

- `Optimized_Update_FC`；
- `Flit_Marker`；
- Flit Sequence Number；
- Replay Command；
- Ack/Nak DLP Symbols。

因此从架构角度看：

```text
传统 DLLP 控制体系
        |
        | 保留普通管理消息
        | 改造确认/重放
        | 增加 Flit 专用控制
        v
Flit Mode DLP 控制体系
```

# 9. 最容易混淆的十件事

1. **Gen6 引入 Flit Mode，不代表 DLLP 被废除。**
2. **DLP 是 Flit 的数据链路控制区域，DLLP 是一种协议消息。**
3. **DLP 中可以放 DLLP，但 DLP 信息不一定是 DLLP。**
4. **Flit Mode 中普通 DLLP 仍是 Type + 24-bit information。**
5. **Flit Mode 的普通 DLLP 没有独立 16-bit DLLP CRC。**
6. **Ack/Nak DLLP 仅用于 Non-Flit Mode。**
7. **Flit Mode 仍需要 Flow Control DLLP。**
8. **Optimized_Update_FC 没有完全替代 UpdateFC DLLP。**
9. **图 3-6 至图 3-15 没画 CRC，不代表 Non-Flit Mode 不需要追加 CRC。**
10. **Reserved 位发送时必须填 0，即使接收端被要求忽略它。**

# 11. 本讲最终模型

```text
数据链路层需要告诉对端：

“TLP 收到了吗？”          -> Non-Flit：Ack/Nak DLLP
                              Flit：Ack/Nak DLP Symbol

“你还能发多少？”          -> InitFC / UpdateFC DLLP
                              Flit 还可用 Optimized_Update_FC

“进入哪个电源状态？”      -> PM DLLP

“我支持哪些特性？”        -> Data Link Feature DLLP

“怎样调整 L0p Link？”     -> Link Management DLLP（Flit Mode）
```

一句话总结：

> **Gen6 的 Flit Mode 没有消灭 DLLP，而是把仍然需要的 DLLP 放进 Flit 的 DLP 控制通道，同时把 Ack/Nak 和 Replay 改造成以 Flit 为中心的专用机制。**

下一步阅读 3.6 时，需要把本讲的两条路径分别接上：

- Non-Flit：Ack/Nak DLLP、TLP Sequence Number、LCRC、Retry Buffer；
- Flit：Flit Sequence Number、DLP Ack/Nak、Flit CRC/FEC、Flit Replay。
