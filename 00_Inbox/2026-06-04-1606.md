**Relative to:** dragon中sw/下的makefile，是一个典型的基于Kbuild/Kconfig 架构的构建脚本，这种架构最初是为 Linux 内核设计的，后来被广泛应用到各类大型嵌入式系统（如 Zephyr、RT-Thread、甚至一些复杂的芯片原厂 SDK）中。

# title: makefile的常用方法

**`scripts_basic:`**：它去调用 `scripts/basic` 目录下的 Makefile。这是 Kbuild 系统的基本操作，通常用来编译一些构建过程中需要的宿主机 C 工具（比如 fixdep 等）

之所以在 `scripts/Makefile` 里面没有直接看到 `fixdep` 的身影，秘密其实藏在你贴出来的最后一行代码里：

Makefile

```
subdir- += basic kconfig
```

这句话的意思是：“去 `basic` 和 `kconfig` 这两个子目录里继续执行”。

如果你进到 **`scripts/basic/`** 目录，你就会发现里面躺着一个 **`fixdep.c`** 文件，以及配套编译它的 Makefile。在上一个关于主 Makefile 的解答中，我们提到了 `scripts_basic:` 这个目标，它最核心的任务就是把这个 `fixdep` 工具编译出来。

那么，**`fixdep` 到底是干什么用的？为什么它这么重要？**

它的全称是 **Fix Dependencies（修复依赖关系）**，它是解决大型 C 语言工程（尤其是带 Kconfig 菜单的工程，如 Linux 内核）“牵一发而动全身”式灾难性重编译的终极武器。

### 1. 痛点：GCC 依赖生成的局限性

在 C 语言编译中，我们通常会让 GCC 帮我们自动生成头文件依赖（利用 `-MD` 或 `-MMD` 参数），生成一个 `.d` 文件。这样，如果你修改了 `a.h`，包含了 `a.h` 的 `main.c` 就会重新编译。

但在 Kconfig 架构下，所有的配置宏（比如 `CONFIG_USB`、`CONFIG_WIFI`）最终都会被汇总到一个巨大的头文件中：`include/generated/autoconf.h`。

几乎所有的 `.c` 文件都会（直接或间接地）包含这个 `autoconf.h`。 **灾难来了：** 假设你只是进 `make menuconfig` 把“某个按键的消抖时间”改了一下，`autoconf.h` 整个文件就被更新了。GCC 一看，所有 `.c` 文件都依赖了 `autoconf.h`，于是**整个工程几千个文件全部重新编译**。这显然是无法接受的。

### 2. 破局：Kbuild 的“拆分配置”设计

为了解决这个问题，Kbuild 系统采用了一个非常巧妙的设计： 当生成 `autoconf.h` 的同时，它会在 `include/config/` 目录下生成成百上千个**空的头文件**，每个头文件对应一个宏。 比如：

- 启用了 `CONFIG_USB`，就生成一个空的 `include/config/usb.h`
    
- 启用了 `CONFIG_WIFI`，就生成一个空的 `include/config/wifi.h`
    

### 3. `fixdep` 的高光时刻

既然有了这些空的头文件，Kbuild 还需要一个工具把它们和 `.c` 文件联系起来。这就是 `fixdep` 的工作：

当 GCC 编译完 `main.c` 产生 `.o` 和 `.d`（依赖文件）后，**`fixdep` 马上出场，拦截这个 `.d` 文件**。

`fixdep` 会像文本搜索器一样，快速扫描 `main.c` 及其包含的所有真实头文件的**源码内容**：

1. 它发现 `main.c` 代码里写了 `#ifdef CONFIG_USB`。
    
2. 它就把对 `include/config/usb.h` 的依赖写入最终的 `.cmd` 依赖文件中。
    
3. 它发现 `main.c` 根本没用到 `CONFIG_WIFI`，就不会把 `wifi.h` 写进去。
    
4. **最关键的一步**：它会把 GCC 生成的对全局 `autoconf.h` 的依赖给**剔除掉**（或者说弱化掉）。
