> [!abstract] 核心结论
> 看完解决几个问题，了解看门狗的原理
> 
> 看门狗到底在防什么？为什么它必须独立？喂狗该放哪？

# 1.看门狗属性

## 1.1 先划清边界：安全性 vs 活性

可靠性文献里把系统性质分两类，这个划分是理解看门狗的钥匙：

| 性质               | 含义        | 违反的样子                  | 看门狗管不管      |
| ---------------- | --------- | ---------------------- | ----------- |
| **Safety（安全性）**  | "坏事永远不发生" | 算错了、写错了寄存器、把 A 口配成 B 口 | **管不了**     |
| **Liveness（活性）** | "好事最终会发生" | 卡住了、不再前进、永远等不到         | **正好是它的领域** |

> 看门狗是**活性监视器**。它检测不到"算错"，只能检测到"不动了"。 
> 推论：任何指望看门狗兜住逻辑 bug 的设计都是幻觉；反过来，任何"系统偶尔就不响应了、复现不了"的场景，看门狗是第一顺位工具。

## 1.2 会导致"不动了"的六类故障

假设在 Dragon 上实际会遇到的概率排序：

1. **死循环 / 状态机卡死** 等一个永远不会置位的硬件状态位是最常见的一种，简称**死等**：这类代码在 flash 驱动、I2C/EEPROM 驱动、link training 轮询里遍地都是

```c
   while (!(REG_STATUS & DONE_BIT));   // 对端没上电 → 永远卡这里
```

2. **PC 跑飞（PC runaway）** 栈溢出踩掉返回地址、函数指针是野指针、跳进了没映射的地址。 
	→ 有可能进 exception handler 后又在里面挂掉（handler 里再触发 exception = 死循环）， 
	→ 也有可能"恰好"落在一段合法代码上继续跑，行为完全不可预测。 
	这是**唯一一类连 exception handler 都救不了**的故障，只有独立硬件能救。
	
3. **中断风暴 / 中断丢失**
    - 风暴：外设中断标志没清干净 → ISR 退出立刻重入 → 主循环再也拿不到 CPU。
    - 丢失：等某个中断唤醒，但中断被意外屏蔽（`mstatus.MIE` 没开、PLIC enable 被覆盖）→ 永远等。
      
4. **RTOS 层的饿死与死锁**
    - 优先级反转：高优先级任务等低优先级任务持有的 mutex，中优先级任务一直跑。
    - 互相等待的两把锁。
    - 某个任务把 CPU 吃满，低优先级任务饿死 —— **注意：此时"系统"看起来是活的**，这正是单点喂狗抓不到、必须多任务签到的原因（见 ）。
      
5. **外部扰动造成的状态破坏** 电源毛刺、ESD、单粒子翻转（SEU）翻掉 RAM/寄存器里一位。 现象随机、无法复现、无法靠代码审查消除。**这是看门狗最原始的设计动机。**
6. **时钟/电源子系统异常** PLL 失锁、时钟被误关、电压掉到 brown-out 边缘但没触发 POR。 ⚠️ 这一类会直接影响你对"狗的时钟源"的选择。

## 1.3 看门狗不能做什么

- **不能替代断言和错误处理。** 已知的、能判断的错误要当场处理，不要"反正狗会救"。
- **不能当调试器。** 但两段式的第一段中断可以变成一个非常好的"死机现场采样器"——这是让看门狗从"兜底"升级成"可观测性工具"的关键。
- **不能保证复位后能恢复。** 如果故障是持续性的（外设挂了、配置数据损坏），复位只会进入无限复位循环。 → 所以必须有**复位计数 + 降级策略**：连续 N 次狗复位 → 进安全模式 / 切 A-B slot / 停在 bootloader 等命令。

## 1.4 对于 Dragon 项目而言

Dragon 是 retimer，firmware 的职责是链路管理、EEPROM/flash 参数、健康上报。对它而言：

- "不动了" 的后果 = 上位机读不到状态、link 状态机停在中间态、热插拔事件漏处理。
- 复位的代价 **不是零**：复位可能打断正在工作的链路。 
  → ⚠️ 必须先确认 **wdt_rst 的复位域**：只复位 CPU 子系统，还是整颗 SoC（含 SerDes / 链路）？ 

## 1.5 本节要点

- 看门狗只管活性，不管正确性。
- 六类故障里，**PC 跑飞和外部扰动**是只有独立硬件能兜的，其余的软件也能部分覆盖。
- 狗咬之后的故事（复位原因、复位循环、降级）和狗咬之前一样重要。



# 2.看门狗硬件

常见的看门狗IP 都会包含什么部分，各司何职？

## 2.1 通用结构

```text
                ┌───────────┐
  时钟源选择 ─-> │  预分频/   │
  (内部RC/外部   │  计数器    │──┬──→ 比较器 A (一段超时) ──→ wdt_int  (中断)
   低速晶振/     │           │  └──→ 比较器 B (二段超时) ──→ wdt_rst  (复位)
   总线时钟)     └───────────┘
                     ↑
               restart / 喂狗 ←── 写保护逻辑 ←── 总线写
                     ↑
                 pause 输入（debug halt / 低功耗）
```
五个部件：**时钟源、计数器、比较级数、写保护、暂停机制**。每一个都是一个设计选择，

## 2.2 时钟源
教科书 “看门狗要有独立时钟”，实际IP会分几种

|档位|做法|抗什么|挡不住什么|
|---|---|---|---|
|最弱|直接用总线时钟（PCLK/APB clk）|软件死循环|时钟树被误关、PLL 失锁、低功耗门控|
|中等|可选外部低速时钟，但**内部逻辑仍由总线时钟驱动**|软件死循环、计数基准更稳|总线时钟停掉时狗也停|
|最强|完全独立的时钟域 + 独立电源域（典型：片上 LSI/LIRC + always-on domain）|几乎全部|整片掉电|

> [!warning]
⚠️ **ATCWDT200 属于"中等"这一档。** DS088 §2 原文： _"The watchdog timer is a single clock domain design clocked by PCLK and the EXTCLK signal does not drive any sequential logics. Instead, the signal is used as a data signal whose rising edge increases the counter... the frequency of EXTCLK must be at least 3 times slower than that of PCLK."
>
>理解：**选 EXTCLK 只是换了个"谁来推计数器加一"的事件源，整个 IP 的触发器仍然吃 PCLK。 PCLK 一停，狗就停，哪怕 EXTCLK 还在跳。**

这个结论的实际后果，写进验收项：

- 进入低功耗 / 时钟门控时 PCLK 还在吗？→ 决定"睡着之后狗还咬不咬"
    
- CPU 卡死时 PCLK 会不会跟着停？（正常情况不会，APB 时钟树独立于 core 的执行）
    
- WDT 所在电源域是否 always-on？

另外一条容易忽略的推论：**EXTCLK 必须比 PCLK 慢至少 3 倍**，否则采样丢边沿、计数偏快。 Dragon 上 EXTCLK=20 kHz、PCLK 在 MHz 量级，这条自动满足；但如果哪天有人想把 EXTCLK 换成高频源"提高分辨率"，这条约束会咬人。


## 2.3 计数器宽度

计数器宽度直接锁死超时上限，ATCWDT200 默认是 16-bit，RTL里定义了 `ATCWDT200_32BIT_TIMER` 才能扩到32-bit，Dragon 实测是 16-bit + EXTCLK 20 kHz


## 2.4 一段式 vs 两段式

|      | 一段式               | 两段式（ATCWDT200）                    |
| ---- | ----------------- | --------------------------------- |
| 行为   | 超时 → 直接复位         | 超时 → 先 `wdt_int`，再过一段 → `wdt_rst` |
| 诊断能力 | 什么都拿不到，只能靠复位原因寄存器 | 第一段能进 ISR，抓 PC / 寄存器 / 任务状态       |
| 风险   | 无                 | ISR 里做太多事 → 复位窗口不够 / ISR 自己也挂了    |

两段式的时序（DS088 Figure 2）：

```text
 喂狗(restart)  
    │  
    ├───── Interrupt Interval (IntTime) ─────┤  
    │                                        ├─ IntEn=1 → 拉高 wdt_int  
    │                                        │  
    │                                        ├──── Reset Interval (RstTime) ────┤  
    │                                                                           ├─ RstEn=1 → 拉高 wdt_rst  
    ▼                                                                           ▼  
   t=0                                    t=IntTime                      t=IntTime+RstTime
```

三条必须记住的语义：

1. **总超时 = IntTime + RstTime**，不是 max，不是 IntTime。
    
2. **`IntEn=0` 不会跳过第一阶段**，只是不拉 `wdt_int` 这根线。第一阶段照样耗时。 （这是 `wdt_reboot()` 里能用 `IntTime=最小 + RstTime=最小` 凑出最快复位的原因。）
    
3. **restart 同时做两件事**：重启中断计时器 **并且取消已经开始的复位计时器**。 → 推论：**进入了复位阶段之后再喂狗，仍然能救回来。** 这是一把双刃剑：如果你的 NMI handler 里"顺手喂了一下狗"，复位就永远不会发生。 （所以 复位原因与故障现场保存 里的 NMI handler 一个 WDT 寄存器都不写。）


## 2.5 为什么需要写保护？

跑飞的 PC 会往随机地址写随机数据。如果关狗只需要一次普通写，那么"程序跑飞"和 "程序跑飞且把狗关了"就只差一个概率。写保护把这个概率从 2⁻¹（写对一个 bit）降到 2⁻¹⁶（写对一个 16-bit 魔数）。

三种常见实现：

| 方案        | 代表                                    | 特点                      |
| --------- | ------------------------------------- | ----------------------- |
| 魔数解锁（一次性） | **ATCWDT200**（`WrEn=0x5AA5`）          | 解锁只对紧接着的一次写有效           |
| 序列锁       | STM32 IWDG（`0x5555` → 写参数 → `0xCCCC`） | 必须按顺序                   |
| 一次性锁定     | 很多 SoC 的 `WDOG_LOCK`                  | 配完就锁死到复位，连合法代码也改不了（最安全） |

> [!notes]
> ⚠️ **ATCWDT200 的关键细节（DS088 §3.2.4）**： _"The register write-protection is enabled again upon the subsequent write to any of the watchdog registers is received."_
> 
> **解锁只"撑"到下一次对任意 WDT 寄存器的写。** 所以：
> 
> WREN = 0x5AA5;  
>  ST   = 1;          /* ← 这次写用掉了解锁，而且它自己是 R/W1C，本来就不需要解锁 */  
>  CTRL = ctrl;       /* ← 这次写被写保护静默丢弃！ */
> 
> 正确形态永远是紧挨着的两条：`WREN` 然后立刻是那一条被保护的写。 而且这两条之间**不能被中断插入**（中断服务里如果也喂狗，就会踩掉你的解锁）→ 必须放临界区。
> 
> 特例：NMI 关不掉。所以只要 NMI handler 里碰 WDT 寄存器，这个竞态就无法用临界区消除 —— 唯一干净的做法是**让 NMI handler 完全不写 WDT 寄存器**。


## 2.6 暂停机制

几乎所有 WDT 都要回答"接了 JTAG、CPU 被 halt 住时，狗还数不数"。 不处理的话，每次你在断点上停 3 秒回来芯片就复位了，根本没法调试。

三种做法：

- IP 有 debug-halt 输入，halt 时自动冻结（很多 ARM SoC）
    
- 有 `DBGEN`/`FREEZE` 之类的寄存器位
    
- **SoC 集成时把某个 pause 信号接到 debug 状态上**
    

ATCWDT200 走的是第三条：有一个 `wdt_pause` 输入（V1.1 加的特性）， _"This signal causes the watchdog timer to pause and delays the triggering of the watchdog interrupt."_

**但 IP 手册管不着它接到了什么。** 在 Dragon 上 `wdt_pause` 接到哪里，是 SoC 集成决定的：

- 接 debug halt → 调试友好，但要注意"量产时会不会被意外拉高"
    
- 悬空/接 0 → 调试时会被狗咬，得靠 CLI 临时关狗
    
- 接了某个低功耗握手 → 睡眠时狗暂停，**这是安全隐患**：系统在睡眠里挂了就没人管了


## 2.7 复位机制

`wdt_rst` 只是 IP 的一根输出线，它复位什么完全由 SoC 决定：

|复位范围|后果|
|---|---|
|只复位 CPU 子系统|外设寄存器保留、链路可能不断；但如果故障在外设里，复不好|
|复位整个 SoC（含 SerDes）|干净，但 retimer 链路一定断，上位机会看到掉链|
|触发完整 POR|RAM 全丢，`.noinit` 崩溃记录也没了 → 诊断链断裂|


## 2.8 本节总结

- 独立性是光谱。ATCWDT200 的 EXTCLK **不是**独立时钟域，整个 IP 由 PCLK 驱动。
    
- 计数器宽度是硬上限，驱动应该拒绝超范围请求而不是 clamp。
    
- 两段式里 restart **会取消复位阶段** —— 所以"救命"的代码千万别顺手喂狗。
    
- 写保护解锁只对**紧接着的一次写**有效，且必须在临界区里。
    
- `wdt_pause` 和复位域都是 **SoC 集成层面的问题**，IP datasheet 回答不了。


# 3. 喂狗的策略

## 3.1 唯一的判据

> **一次喂狗 = 一份声明："从上次喂狗到现在，系统完成了至少一整圈有意义的工作。"**

所以每次你写下 `wdt_feed()` 的时候，要能回答： **执行到这一行，证明了什么？** 
如果答案是"证明这行代码被执行了"，那就是废话， 因为任何代码被执行都能证明这一点。


## 3.2 反模式图鉴
### ❌ 反模式 1：定时器/SysTick 中断里喂狗

 void timer_isr(void) { wdt_feed(); }

证明了什么？**只证明了定时器中断还能进。** 业务任务全死光了，这只狗也不会咬。 这是工业界最常见的"装了等于没装"。

### ❌ 反模式 2：FreeRTOS software timer / idle hook 里喂狗

同上，只证明 timer service task 或 idle task 还活着。更糟的是： **idle task 能跑恰恰说明系统闲着** —— 而高优先级任务把 CPU 吃满时 idle 根本不跑， 这种情况反而会被误咬，逻辑是反的。

### ❌ 反模式 3：每个任务都能直接喂狗

三个关键任务 A/B/C，A 死锁了，B 还在喂。狗永远不咬。 **只要存在两个及以上的喂狗调用点，喂狗就退化成了"或"逻辑**，而你需要的是"与"。

### ❌ 反模式 4：长阻塞操作前后"补喂"

 wdt_feed();  
 flash_erase_sector();   /* 可能 400 ms */  
 wdt_feed();

这在掩盖问题：你实际上是在说"这段时间不受监控"。正确做法是 **把最坏耗时算进超时预算**（§3.4），或者把长操作拆成可中断的小步。

### ❌ 反模式 5：喂狗和业务解耦成"心跳"

 for (;;) { watchdog_alive(); }   /* 卡在这个循环里会疯狂上报健康 */

`alive` 只证明"代码在跑"。要用 **progress（递增的业务进展序号）**：

 for (;;) {  
     if (process_one_complete_cycle() == 0) {  
         wdg_report_progress(WDG_CLIENT_LINK, ++progress);  
     }  
 }

supervisor 只有看到**序号变化**才认为有进展。序号不动 = 没进展，哪怕任务还在跑。

### ❌ 反模式 6：调试时关狗，然后忘了开

用编译期开关控制，并且**上电时无条件打印狗的实际状态**（`CTRL` 原值）， 让"狗是关的"这件事在日志里没法藏。

### ❌ 反模式 7：故障判定后又恢复喂狗

supervisor 判定 A 超期 → 写了 crash record → 结果 A 又活过来了 → 继续喂狗 → 不复位。 留下一条**没有对应复位的陈旧记录**，下次正常暖复位时会误报。

> **规则：故障一旦锁存，本次启动周期内永久停止喂狗，确定性地走到硬件复位。**
