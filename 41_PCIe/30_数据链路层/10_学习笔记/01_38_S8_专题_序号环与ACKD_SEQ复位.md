> [!abstract] 这篇专题在讲什么
> §3.6 里有四处 `mod 4096` 的判断（Equation 3-1、Figure 3-18 的两个判断式、§3.6.3.1 的重复/乱序判定）。数字太大，在脑子里转不动。
> **这里全部换成一个 16 格的钟：序号 0~15，15 之后回到 0，半圈 = 8。** 规则一个字不改，只是数字变小。最后一节再换回 4096。
>
> 顺序：**判断工具 → 接收端 5 个 case → 为什么「一定」→ 发送端 6 个 case → 换回 4096**。
> 接收端先讲，因为「往前」和「往后」两种情况在接收端都真实存在，最直观。

# 0. 先决条件：判断工具 ^tool

```
距离 d = (看到的号 − 我的参考号) mod 16
```

然后只看 d 落在哪个区间：

| d | 含义 |
|---|---|
| **0** | 就是参考号本身 |
| **1 ~ 7** | 一定是「**往前**」（更新） |
| **8 ~ 15** | 一定是「**往后**」（更旧） |

> [!note] mod 16 的算法
> 结果是负数就 **+16**。比如 `(1 − 14) = −13 → −13 + 16 = 3`。
> 硬件上就是 4 位无符号减法，自动回绕，不用想负数。

PCIe 里有两个地方要做这种判断：

| 谁 | 参考号 | 看到的号 |
|---|---|---|
| **接收端**判断收到的 TLP | `NEXT_RCV`（下一个期望收到几号） | TLP 的序号 |
| **发送端**判断收到的 Ack/Nak | `ACKD`（最后确认到几号） | Ack/Nak 里的序号 |

> [!warning] 上面那个「一定」是有前提的
> d = 13 在钟面上也可以理解成「往前 13 步」。凭什么排除？靠一条规定——**在途的包不到半圈**。第 2 部分专门讲。先用起来。

---

# 1. 第一部分：接收端 ^rx

接收端有一个变量 `NEXT_RCV`，表示「我下一个期望收到几号」。收到一个序号为 `seq` 的 TLP（LCRC 已通过）后计算：

```
d = (seq − NEXT_RCV) mod 16
```

| d | 判断 | 动作 |
|---|---|---|
| **0** | 正是我要的 | 接收，`NEXT_RCV + 1` |
| **1 ~ 7** | 往前：中间有包丢了 | 丢弃，发 **Nak** |
| **8 ~ 15** | 往后：重复包（以前收过） | 丢弃，发 **Ack** |

Ack 和 Nak 里填的数都是 **`NEXT_RCV − 1`**，意思是「这个号之前我都收好了」。

## Case 1：正常接收

```
NEXT_RCV = 6，收到 6 号
d = (6 − 6) mod 16 = 0
```

→ 正是期望的包。接收，`NEXT_RCV` 变成 7。

## Case 2：中间丢包（往前）

发送端发了 6、7、8，其中 6、7 在链路上丢了，接收端只收到 8。

```
NEXT_RCV = 6，收到 8 号
d = (8 − 6) mod 16 = 2        → 落在 1~7，往前
```

→ 8 比期望的 6「往前 2 步」，说明 6、7 丢了。丢弃 8，发 **Nak(5)**（「我只正确收到 5 号为止」），发送端从 6 开始重发。
Q：到底是NAK几开始发？报回NAK(x)?

> [!note] 顺带发生的事：`NAK_SCHEDULED` 置位
> 发完这个 Nak 后标志置位。接着如果 9、10 也到了（d = 3、4，同样「往前」），**只丢弃，不再发 Nak**。
> 等重发的 6 号到了（d = 0），接收、`NEXT_RCV` 变 7、清标志。一次丢包只喊一次。

## Case 3：丢包 + 跨越回绕（往前）

发送端发了 15、0、1，其中 15、0 丢了，接收端只收到 1。

```
NEXT_RCV = 15，收到 1 号
d = (1 − 15) mod 16 = −14 + 16 = 2   → 落在 1~7，往前
```

→ 直觉上「1 比 15 小」，好像是旧包，但实际上 1 在 15 的前面 2 步（15 → 0 → 1）。mod 运算给出了正确答案：丢了 15、0，发 **Nak(14)**。

## Case 4：重复包（往后）

发送端发了 3、4、5，接收端全部正确收到，`NEXT_RCV` 变成 6，并回复 Ack(5)。但 Ack(5) 在链路上损坏了，发送端没收到。发送端等到 `REPLAY_TIMER` 超时，把 3、4、5 重新发了一遍。

接收端收到重发的 3 号：

```
NEXT_RCV = 6，收到 3 号
d = (3 − 6) mod 16 = −3 + 16 = 13   → 落在 8~15，往后
```

→ 3 在 6 的后面 3 步，是以前收过的重复包。丢弃，并回复 **Ack(5)**，告诉发送端「5 号之前都收到了，别再重发了」。

接着收到 4、5：

```
收到 4：d = (4 − 6) mod 16 = 14   → 往后，重复，丢弃
收到 5：d = (5 − 6) mod 16 = 15   → 往后，重复，丢弃
```

> [!note] 重复包必须回 Ack，这一点不受 `NAK_SCHEDULED` 影响
> 重复包出现本身就是「我的 Ack 丢了」的证据。不回 Ack，发送端会一直重发到 `REPLAY_NUM` 溢出、把链路拖去重训练。

## Case 5：重复包 + 跨越回绕（往后）

接收端已经收到 14、15、0，`NEXT_RCV = 1`。Ack(0) 丢了，发送端重发 14、15、0。

```
NEXT_RCV = 1，               收到 14 号
d = (14 − 1) mod 16 = 13   → 落在 8~15，往后
```

→ 直觉上「14 比 1 大」，好像是新包，但实际上 14 在 1 的后面 3 步（14 → 15 → 0 → 1）。mod 运算判断为重复包，丢弃，回复 **Ack(0)**。

## 接收端小结 ^rx-summary

| Case | `NEXT_RCV` | 收到 | d | 判断 | 回什么 | 直觉会不会错 |
|---|---|---|---|---|---|---|
| 1 | 6 | 6 | 0 | 期望的包 | （到点后 Ack(6)） | 不会 |
| 2 | 6 | 8 | 2 | 往前（丢包） | Nak(5) | 不会 |
| 3 | 15 | 1 | 2 | 往前（丢包） | Nak(14) | **会**，直觉以为 1 是旧的 |
| 4 | 6 | 3 | 13 | 往后（重复） | Ack(5) | 不会 |
| 5 | 1 | 14 | 13 | 往后（重复） | Ack(0) | **会**，直觉以为 14 是新的 |

**Case 3 和 Case 5 说明了为什么不能直接比较大小，必须用 mod 距离。**

# 2. 第二部分：为什么「一定」——没有半圈规定会怎样 ^why-half

上面的判断说 d = 13「一定是往后」。但在钟面上，13 也可以理解成「往前 13 步」。凭什么排除这种可能？

**因为协议规定：发送端在途（已发未确认）的包最多 7 个，不到半圈。**

## 这个 7 是从哪来的

发送端有 `NEXT`（下一个要发的号）和 `ACKD`（最后确认到的号），Equation 3-1 在小钟上是：

```
(NEXT − ACKD) mod 16 ≥ 8   →  停止接收新 TLP
```

左边算的是「未确认数 + 1」（`ACKD` 是最后一个已确认，`NEXT` 是下一个还没发的，中间夹着的才是在途）。所以 **≥ 8 就停 ⇔ 在途 ≥ 7 就停**，在途最多 7 个。

```
ACKD = 5：NEXT = 12 → (12 − 5) = 7 → 还能发（在途 6~11，共 6 个）
          NEXT = 13 → (13 − 5) = 8 → 停       （在途 6~12，共 7 个）
```

## Case 6：规定如何保证「一定往后」

接收端 `NEXT_RCV = 6`，意味着 5 号及之前都已正确收到。接收端回复的最新 Ack 至多是 5，所以发送端的 `ACKD` 至多是 5。而发送端最多只能在 `ACKD` 之后再发 7 个包。

最极端情况：发送端的 `ACKD` 就是 5，它最多发到 5 + 7 = 12 号。

```
可能出现的新包：6, 7, 8, 9, 10, 11, 12   → d = 0 ~ 6
```

所以接收端**不可能**收到比 12 更「往前」的包。如果收到 3 号（d = 13），它不可能是「往前 13 步的新包」，只能是重复的旧包。**规定排除了其中一种解释，剩下的那一种就是「一定」。**

> [!note] 反过来看旧包
> 发送端能重发的最旧的包是 `ACKD + 1`，而 `ACKD ≥ NEXT − 8 ≥ NEXT_RCV − 8 = −2 ≡ 14`，所以最旧的重发包是 15 号，d = (15 − 6) mod 16 = 9。
> **遵守规定时，新包 d ∈ 0~6，旧包 d ∈ 9~15。7 和 8 根本出现不了。** 这就是为什么第 4 部分说「边界符号不影响运行」。

## Case 7：如果违规，允许在途 12 个包

假设发送端不遵守规定，`ACKD = 5`，一口气发了 6、7、8、…、15、0、1（12 个包）。

链路上 6~14 这 9 个包全丢了，接收端只收到 15 号：

```
NEXT_RCV = 6，收到 15 号
d = (15 − 6) mod 16 = 9   → 落在 8~15，判断为「往后，重复包」
```

- **实际情况**：15 是新包，前面丢了 9 个，应该发 Nak 立刻重传。
- **错误判断**：当成重复包，丢弃并回 Ack(5)。

发送端收到 Ack(5)，和自己的 `ACKD` 相等，没有新确认，不会触发 replay；`REPLAY_TIMER` 也不会因为这条 Ack 重置（它没有确认任何在途包）。接着到的 0、1 号同样被判成重复。**Nak 这条快速路径完全失效，只能干等超时兜底**，而且日志里记的是「重复包」而不是「丢包」——排查会被带偏。

**这就是「必须留一半」的原因：在途包一旦超过半圈，同一个 d 值就可能对应两种真实情况，判断必然出错。**

# 3. 第三部分：发送端判断 Ack/Nak ^tx

发送端有 `ACKD`（最后确认到几号），收到 Ack(n) 或 Nak(n) 后计算：

```
d = (n − ACKD) mod 16
```

| d | 判断 | 动作 |
|---|---|---|
| **0** | 没有新确认 | 不清理（若是 Nak，则重发全部在途包） |
| **1 ~ 7** | 往前：对方新确认了 d 个包 | 清理这些包，`ACKD` 更新为 n；重置 `REPLAY_NUM` 和 `REPLAY_TIMER`（若是 Nak，再重发剩下的） |
| **8 ~ 15** | 往后：不合理的号码 | **异常**（见 Case 13） |

## Case 8：正常新确认

```
ACKD = 5，在途：6, 7, 8
收到 Ack(7)
d = (7 − 5) mod 16 = 2   → 往前
```

→ 新确认了 6、7 两个包。清理 6、7，`ACKD` 变成 7，在途剩下 8。

## Case 9：新确认 + 跨越回绕

```
ACKD = 14，在途：15, 0, 1
收到 Ack(0)
d = (0 − 14) mod 16 = −14 + 16 = 2   → 往前
```

→ 直觉上「0 比 14 小」，好像是旧确认，但实际是往前 2 步：确认了 15、0。清理它们，`ACKD` 变成 0，在途剩下 1。

## Case 10：复位后的第一个 Ack（why 初始化值为FFFh）^case10

复位后 `ACKD = 15`（小钟上的「FFFh」），发送端发了 0、1。

```
ACKD = 15，在途：0, 1
收到 Ack(0)
d = (0 − 15) mod 16 = −15 + 16 = 1   → 往前
```

→ 确认了 0 号，清理，`ACKD` 变成 0。✅

**如果复位时 `ACKD = 0`：**

```
ACKD = 0，在途：0, 1
收到 Ack(0)
d = (0 − 0) mod 16 = 0   → 没有新确认
```

→ 0 号明明被确认了，却被判断为「没有新确认」，**0 号永远清不掉**。❌

**再看复位后对方发的第一条「空 Ack」**（接收端 `NEXT_RCV = 0`，它填的是 `NEXT_RCV − 1 = 15`）：

```
ACKD = 15，收到 Ack(15)：d = 0 → 没有新确认，合法，什么都不做 ✅
ACKD = 0， 收到 Ack(15)：d = (15 − 0) mod 16 = 15 → 往后 → 协议错误 ❌
```

→ 复位成 0 的话，**链路刚起来、一个包都没发，对方的第一条合法 Ack 就被判成错误**。

> [!important] 两端用的是同一种编码
> `ACKD` 的语义是「**最后一个**已确认」，接收端 Ack 里填的是「**最后一个**已收到」。复位时两边都是「0 的前一个」= 15。
> **`FFFh` 和 `NEXT_RCV − 1` 是一对，改任何一边都对不上。**

## Case 11：Nak 且没有新确认

```
ACKD = 5，在途：6, 7, 8
收到 Nak(5)
d = (5 − 5) mod 16 = 0
```

→ 对方说「只收到 5 号为止」，没有新确认。不清理，重发 6、7、8。

## Case 12：Nak 带部分确认

```
ACKD = 5，在途：6, 7, 8
收到 Nak(6)
d = (6 − 5) mod 16 = 1   → 往前
```

→ **先**把 6 当作已确认清理掉，`ACKD` 变成 6，**然后**重发剩下的 7、8。顺序反了会把 6 也白重发一遍。

## Case 13：往后的号码 ^case13

```
ACKD = 5，在途：6, 7, 8
收到 Ack(3)
d = (3 − 5) mod 16 = 14   → 往后
```

→ 3 号早在之前就被确认过了，对方不应该再发 Ack(3)。

> [!important] spec 原文（§3.6.2.2）
> > If the Sequence Number specified by the AckNak_Seq_Num **does not correspond to an unacknowledged TLP, or to the value in ACKD_SEQ**, the DLLP is **discarded**. This is a **Data Link Protocol Error**, which is a reported error associated with the Port (see Section 6.2).
>
> PCIe 是点对点链路，DLLP 按顺序到达，接收端回复的序号只会增加，正常情况下发送端**不应该**收到往后的 Ack/Nak。所以规定是：丢弃 + 上报错误。
> （spec 唯一放过的是 `n == ACKD` 的重复 Ack，见 Case 11 的 d = 0。）

**同理，下面这个情况也属于异常：**

```
ACKD = 5，在途：6, 7, 8
收到 Ack(11)
d = (11 − 5) mod 16 = 6   → 在 1~7，「往前」
```

→ 虽然 d 在往前的区间，但 9、10、11 号根本没发出去过，对方不可能确认它们。这同样是协议错误。

> [!note] 所以发送端实际检查的是两头
> Figure 3-18 用两个判断式画了一个窗口，小钟版：
> ```
> 判断式一：((NEXT − 1) − n) mod 16 ≤ 8    ← 挡「太新」：n 不能超过我发出的最后一个
> 判断式二：(n − ACKD) mod 16 < 8           ← 挡「太旧」：n 不能比已确认的还旧
> ```
> `d = (n − ACKD) mod 16` 就是判断式二。**d 落在 1~7 只是必要条件，还要 n 是某个在途包的序号。**
> Ack(11)：在途是 6、7、8，`NEXT = 9`，判断式一 `(8 − 11) mod 16 = 13 > 8` ✗ → 挡下。
> Ack(3)：判断式二 `14 ≥ 8` ✗ → 挡下。
> 两式合起来 = **n 必须落在 [ACKD, NEXT − 1]**。

## 发送端小结 ^tx-summary

| Case | `ACKD` | 在途 | 收到 | d | 判断 |
|---|---|---|---|---|---|
| 8 | 5 | 6,7,8 | Ack(7) | 2 | 确认 6、7 |
| 9 | 14 | 15,0,1 | Ack(0) | 2 | 确认 15、0（跨回绕） |
| 10 | 15 | 0,1 | Ack(0) | 1 | 确认 0（复位值正确） |
| 10' | 0 ❌ | 0,1 | Ack(0) | 0 | 误判为没有新确认，0 永远清不掉 |
| 10'' | 0 ❌ | — | Ack(15)（空 Ack） | 15 | 第一条合法 Ack 被判协议错误 |
| 11 | 5 | 6,7,8 | Nak(5) | 0 | 不清理，重发 6、7、8 |
| 12 | 5 | 6,7,8 | Nak(6) | 1 | 清理 6，重发 7、8 |
| 13 | 5 | 6,7,8 | Ack(3) | 14 | 往后，协议错误 |
| 13' | 5 | 6,7,8 | Ack(11) | 6 | 「往前」但没发过 → 判断式一挡下，协议错误 |

# 4. 第四部分：把小钟换回 4096 ^back-to-4096

| 小钟 | spec |
|---|---|
| 序号 0 ~ 15 | 序号 0 ~ 4095 |
| mod 16 | mod 4096 |
| 半圈 8 | 2048 |
| d = 1 ~ 7 往前 | d 在前半圈 |
| d = 8 ~ 15 往后 | d 在后半圈 |
| 在途最多 7 个 | 在途最多 **2047** 个 |
| `ACKD` 复位为 15 | `ACKD_SEQ` 复位为 **FFFh** |
| Ack/Nak 填 `NEXT_RCV − 1` | `AckNak_Seq_Num = NEXT_RCV_SEQ − 1` |

## 4.1 方向对照：spec 的接收端公式是反着写的

本文统一用 `d = (看到的号 − 参考号)`。spec 里发送端的判断式二和这个方向一致，但**接收端的公式是反过来写的**：

| | 本文 | spec 原文 |
|---|---|---|
| 接收端重复判定 | `(seq − NEXT_RCV) mod 16` 落在 **8 ~ 15** → 重复 | `(NEXT_RCV_SEQ − Seq) mod 4096 ≤ 2048` → 重复 |
| 发送端判断式二 | `(n − ACKD) mod 16` 落在 **0 ~ 7** → 合法 | `(AckNak_Seq_Num − ACKD_SEQ) mod 4096 < 2048` → 合法 |

两种写法是同一件事（把减数和被减数对调，前半圈和后半圈就互换）。**读 spec 时注意谁减谁。**

## 4.2 四条规则的边界，照抄原文 ^boundary

| 规则 | spec 原文 | 比较符 |
|---|---|---|
| Equation 3-1 | `(NEXT_TRANSMIT_SEQ − ACKD_SEQ) mod 4096` | **≥ 2048** → 停止接收新 TLP |
| Fig 3-18 判断式一 | `((NEXT_TRANSMIT_SEQ − 1) − AckNak_Seq_Num) mod 4096` | **≤ 2048** → 通过 |
| Fig 3-18 判断式二 | `(AckNak_Seq_Num − ACKD_SEQ) mod 4096` | **< 2048** → 通过 |
| §3.6.3.1 重复判定 | `(NEXT_RCV_SEQ − TLP Sequence Number) mod 4096` | **≤ 2048** → 重复 |

spec 中每条公式在 2048 这个边界上用 `<` 还是 `≤` 不完全一样。**但只要在途包数遵守规定、达不到半圈，实际运行中根本不会出现 d 正好等于半圈的情况**（小钟上 7 和 8 都不会出现，见 Case 6 的注），所以边界值不影响理解整个机制。**照抄就行，不用套口诀。**

## 4.3 「留一半」的代价是什么

量程从 4095 缩到 2047。spec 的 Implementation Note 说 Ack Latency Limit 保证**序号范围永远不会成为限制因素**——Ack 会在远早于 2047 个未确认之前回来。**所以这一半是免费的。**

# 5. Summary^one-liner

> 序号是一个钟。钟面上的距离分不出方向，于是协议规定在途不到半圈（小钟 7，spec 2047），这样「往前」和「往后」就各占半圈、一定能分开。
> 接收端用它分「丢包」和「重复」，发送端用它分「新确认」和「非法」。
> `ACKD` 复位成「0 的前一个」（小钟 15，spec FFFh），是因为它的语义是「最后一个已确认」，和接收端 Ack 里填的「最后一个已收到」是同一种编码。
